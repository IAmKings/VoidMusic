# 正式发布前性能验证清单

## 目的与执行时机

本清单是 Void Music 正式发布候选版（RC）的人工性能门禁。当前开发阶段暂无高/中/低三档独立真机，因此设备矩阵与前台连续演奏 20 分钟不作为本阶段阻塞项，但必须在正式发布前完成，不能用模拟器或单机强制切档代替三档真机结果。

仅对最终签名 RC 包执行。报告必须记录版本号、Git 提交、APK SHA-256、设备型号、SoC、内存、Android 版本、电量、环境温度和应用性能档位。

## 设备矩阵

至少准备三台不同性能层级的实体 Android 设备，每档至少一台：

| 设备档位 | 应用验证档位 | 目标分析 FPS | 关键配置 |
|---|---|---:|---|
| 低档 | LOW | 15 | 480×360、CPU、单手、0.25 倍色块分割 |
| 中档 | MEDIUM | 24 | 640×480、GPU、双手、0.5 倍色块分割 |
| 高档 | HIGH | 30 | 640×480、GPU、双手、原尺寸色块分割 |

设备层级以实际硬件能力和应用在目标档位下的持续表现共同确认。报告不得只写“高/中/低”，必须附完整硬件信息。运行时因省电模式或 Thermal Status ≥ MODERATE 自动降到 LOW 时，应同时记录用户首选档位和实际生效档位。

## 固定场景

- 使用同一套四种彩色物件、相同摆位、机位、距离、光照和背景。
- 使用同一套连续同色、四颜色轮换、双手交替击打节奏；扬声器音量保持一致。
- 每台设备测试前静置至 Thermal Status 0 或 1，电量不低于 40%，关闭省电模式。
- 每台设备使用同一签名 RC APK；发生代码、模型、音频资源或性能配置变化后，三档结果全部失效并重测。

## 单台设备执行步骤

1. 冷启动并完成首次识别，记录启动耗时、初始温度、PSS、Native Heap、Bitmap/Mat 数量和有效性能档位。
2. 连续前台演奏 20 分钟；在 0、5、10、15、20 分钟采集 HUD、内存、GC、温度、Thermal Status、Crash/ANR 和音频状态。
3. 演奏中覆盖同色快速连击、四颜色循环切换和双手交替；记录漏声、重复触发、错误音色、卡顿和触感变化。
4. 完成扬声器 → 蓝牙耳机 → 扬声器切换，确认实际出声位置、恢复时间、Oboe/SoundPool 后端、丢音和欠载。
5. 将应用置于后台 20 分钟后恢复，确认相机、手部、色块和声音无需重启即可恢复。
6. 测试后静置 60 秒再采集一次内存，确认 Bitmap、Mat、Native stream 和线程没有持续增长。

## 必须记录的指标

| 指标 | 发布判定 |
|---|---|
| 分析 FPS / 手部结果 FPS | 正常温度下达到当前有效档位目标的 90%；发生热降档后按 LOW 目标判定 |
| 采集 → 手部回调 P50/P95 | P95 < 260 ms |
| 回调 → 消费 P50/P95 | 不形成持续排队；P95 不高于一个当前档位帧周期 |
| 色块分割 P50/P95 | P95 ≤ 25 ms |
| 鼓区缓存年龄 P50/P95 | P95 < 260 ms |
| 候选 → 音频提交 P50/P95 | P95 ≤ 10 ms |
| 击打 → 实际出声 | 扬声器目标 P95 ≤ 180 ms、硬上限 260 ms；必须用外部声学方法测量，HUD 不能替代 |
| 音频稳定性 | 稳态演奏 `droppedTriggers=0`；无可感知漏声，xRun 不持续增长 |
| 20 分钟稳定性 | 无崩溃、ANR、黑屏、相机停流、识别失效或音频中断 |
| 温升与热策略 | 记录起止温度和峰值；不得进入 SEVERE 或更高热状态，自动降档后仍可正常演奏 |
| 内存与资源 | PSS/Native Heap、Bitmap/Mat、线程和 Native stream 不随时间持续单调增长；静置后可回落或稳定 |
| 后台恢复 | 20 分钟后无需杀进程或重启应用即可恢复全部演奏链路 |

蓝牙端到端声学延迟受耳机编解码与系统缓冲影响，单独记录，不与扬声器 260 ms 硬门禁混算；但路由切换、触发完整性和主观节奏可用性仍必须通过。

## 发布结论模板

每台设备给出 PASS/FAIL 和原始证据路径。只有三档设备全部 PASS，且没有未解释的性能退化、资源增长或稳定性故障，才能通过正式发布前性能门禁。任何一档 FAIL 都应关联缺陷、修复版本和复测记录，不允许用其他档位结果覆盖。

- 独立高/中/低三档真机暂不可用。
